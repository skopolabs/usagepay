# 01.2 — UsagePay: Product Foundation and Market Positioning

**Document version:** 1.1.0 · **Strategy reviewed:** 2026-10-25 · **HackMeridian begins:** Sunday, 2026-10-25 · **Status:** Product definition; 01.1 owns implementation and complete roadmap · **Authority:** 01.1 for all technical acceptance and milestones

## 0. Executive product decision

**Build the evidence layer between external metering systems and authorized Stellar MPP channel settlement.** Do not build a generic machine-commerce control plane, wallet, metering protocol, EV charging app, SaaS billing alternative or lending/privatization system. The working product name is **UsagePay**. The working tagline *“Infrastructure for the machine economy”* is directional, not a security assertion (§0.1).

**Technical proposition:** a third party can inspect original device/service evidence, verify available origin signatures, replay tariff accounting, inspect the payer-authorized channel commitments, locate actual Stellar settlement and understand discrepancies or gaps. This is an **application-level audit chain**. The current one-way-channel contract does **not** check meter signatures, tariffs or external session IDs before paying an authorized amount.

**Economic proposition:** maybe operators need (A) independent reusable evidence tooling and/or (B) managed always-on channel settlement. These are independent product/business hypotheses, not interchangeable benefits.

## 0.1 Positioning and messaging (single source for the UI, README and pitch)

UsagePay is **not an EV charging product.** It is the proof layer for machine payments: any service a machine can measure and bill per unit. EV charging is the **demo use case**, chosen because everyone understands a charger and a kilowatt-hour. Every public artifact must leave a reader with that order: the category first, the demo second.

**Kicker:** *Infrastructure for the machine economy.* Chosen on 2026-10-25 over *Machines pay for what they use.* because it sells the category to a commercial reader. It names the category UsagePay is building for, not a production deployment: the P0 is a Testnet prototype.

**First sentence (H1 of the demo, first line of the README and the pitch):** **UsagePay enables verifiable machine-to-machine payments for metered services on Stellar.**

**One-line promise:** *Every payment carries its proof:* the signed measurement, the price applied, the payer's approval and the Stellar settlement, checkable by anyone.

**Use-case framing:** "Demo use case: EV charging. The same flow fits any service a machine can measure: energy, compute time, connectivity, equipment hours, water." These are illustrative categories, not built adapters or customers.

**Why Stellar MPP alone is not enough.** MPP answers two questions: how much did the payer authorize, and did it settle? It cannot answer the third: *for what?*

- An MPP voucher signs a channel and a running total. It carries no reading, no unit and no price.
- The channel contract pays any amount the payer signed. It never sees the meter.
- So any usage log can be shown next to a valid payment, and nobody can prove they belong together.

UsagePay adds the missing link, on top of MPP and without a new contract:

1. Signed readings are checked before anyone pays.
2. Pricing can be replayed by anyone, to the exact base unit.
3. A payer-signed receipt binds each voucher to its exact evidence, channel and network.
4. Evidence is sealed before settlement (E0) and linked to the transaction after it (E1).
5. An independent auditor re-checks everything and holds no keys.

**Fits what is already deployed** (§4; 01.1 §3–4):

- **No new hardware.** Built to read the meter data that existing standards already carry; in EV charging, OCPP with OCMF signed readings. No new device, no firmware change.
- **No new payment protocol.** Payments use Stellar MPP and its existing one-way channel contract, unchanged. No new contract, no fork.
- **Beside existing systems.** Charger management, billing and roaming (CSMS, OCPI) keep their role. UsagePay adds the evidence that links their records to the payment.

Always pair this with the honest qualifier:
- the demo meter is simulated and OCPP-shaped, not certified and not OCPP or OCMF conformant;
- meters that sign only start and end readings need provisional amounts reconciled at the end, which is on the roadmap.

**Brand line:** "UsagePay" with a small raised "on Stellar". Never "by Stellar": UsagePay is built on Stellar, not made or endorsed by the Stellar Development Foundation. Do not use the official Stellar logo without checking the Stellar brand guidelines.

**Value by party (no cost-savings claim until measured, §2 and 01.4):**

| Party | Message |
|---|---|
| Payer | Pays only for signed, priced usage; the budget is enforced on its side; its keys never leave it |
| Provider | Paid as it delivers, not at invoice time; many vouchers settle in one transaction |
| Finance, auditor or partner | Verifies from public evidence, without access to either party's systems |
| Developers | Open evidence format, verifier and test vectors on top of Stellar MPP; no new contract, no fork |

**Proof points:** only figures read from the demo bundle (vouchers per transaction, independent checks passed, attack and failure scenarios refused, real Stellar Testnet).

**Honesty guardrails.** The P0 implements **one adapter: energy in Wh**. Say "built for any metered service; this demo runs the energy adapter", never "the code supports any unit". Never say the blockchain proves consumption, the contract rejects false meters, the meter is certified, the product is the first of its kind, or that it saves costs. §5, §7 and 01.1 §5 still bound every claim.

## 1. Problem framing

The relevant deficiency is not lack of a machine payment mechanism: domain protocols already know sessions, tariffs, signed readings and invoices, while MPP already handles cumulative payment authorization. The **testable pain** is correlating three independently maintained states across counterparties: (i) what an external meter reports as delivered, (ii) what the authorized payer has committed financially, and (iii) what actually settled.

Today, disputes may involve one party's CSMS logs, another party's CDR or invoicing system, and an unrelated payment reconciliation. We must find out whether **existing EV systems already provide sufficient correlation**, and whether adding a cryptographically attributable third ledger improves real costs.

The product is unnecessary for direct, fixed-price API calls; ordinary subscription SaaS; simple operator-only internal accounting; use cases where no independent evidence is required; or where direct CSMS-to-MPP glue solves everything at negligible maintenance cost.

## 2. Buyers, users and contracting relationships

| Role | Current initial hypothesis | Wants | Unknown |
|---|---|---|---|
| Fleet operator | **Payer of record** in chosen demo contract | Spend caps, per-service evidence, fewer disputes | Whether they want/pay for stablecoins; who holds signing key |
| CPO / CSMS | Service operator/payee | More predictable settlement, verifiable claims, monitoring | Current CDR maturity, costs, real channel appetite |
| eMSP | Alternative contractual payer or clearing intermediary | Roaming reconciliation | Whether existing hub makes integration redundant |
| Platform developer | Adopter of OSS SDK | Verified adapter and evidence formats | Repeat adoption outside EV |
| Managed-service customer | CPO/payee or fleet depending obligation | High availability, fast channel recovery, alerting | SLA value, settlement liability, security requirements |

**Do not claim all fleets pay CPOs directly.** Roaming contracts vary. The demo chooses a fleet–CPO pair for clarity, and explicitly labels the simplification.

## 3. Value proposition by stakeholder

**Payer (fleet):** policy authority stays with fleet, capped cumulative exposure, signed acknowledgment of what it was willing to pay, and a replayable record of why each incremental payment was offered.

**Payee (operator):** correlate delivered metering evidence with collectable commitments; monitor channel risk; receive testnet settlement. The operator must never assume a reading alone creates an enforceable payment; the payer's signature is the financial authorization.

**Developer ecosystem:** open SDK/adapter + reproducible test vectors for external meter evidence and MPP channel operations. An OSS library may have ecosystem value even with no commercial buyer.

**Stellar ecosystem:** an integration demonstration could lead to more real stablecoin utility, channels and developer tooling, but speculative channel counts and network transaction revenue are not forecasts. Channels deliberately amortize on-chain transactions.

## 5. Evidence trust model

### Five different propositions

1. **Origin:** given byte string was signed by a key claimed to belong to a meter. Check raw bytes/key registry, not just a signature boolean.
2. **Physical validity:** actual metered quantity and legal certification are separate; cannot be inferred from origin signature alone.
3. **Accounting:** price computed from the correct units, tariff effective interval and rounding policy.
4. **Financial authorization:** payer signed an exact **cumulative monetary value** for the pinned channel and network; MPP signature does not bind an OCMF digest natively.
5. **Settlement:** specified Stellar transaction settled or closed the channel; audit trail mapping is application-level, not an atomic physical-payment condition.

L0 = operator assertion; L1 = authenticated system source; L2 = meter-signed record. Add `certification_status ∈ {simulated, unknown, vendor_attested, independently_checked}`; L2 **does not** imply legal certification. Track whether readings are `intermediate_unsigned`, `intermediate_signed`, or `terminal_signed`. Signed intermediate reading is optional by OCPP/OCA configuration and hardware capability.

### Verification semantics (product expectations only)

Customers and third-party integrators should be able to see **separate** results for meter-origin signature, provenance/certification, tariff replay, payer financial authorization, application-level correlation and actual chain settlement. An overall green badge must never imply certified physical truth or on-chain meter enforcement.

**The authoritative sample E0/E1 JSON, end-to-end diagrams, money examples, rejection tests and binding/anchoring constraints are in [01.1 §8–9](../../01.1-usagepay-technical-architecture-and-roadmap.md).** They are intentionally not reproduced here, so the engineering team does not maintain two competing schemas. Those examples are illustrative; [SPEC 00](../../specs/00-shared-contracts-and-engineering-rules.md) defines the final serialization.

## 6. Security, policy and payment operations

- **Separation of authority:** the fleet's signer checks proposed amount and budget locally; a CPO server cannot be the sole policy arbitrator for the payer.
- **Serializability:** exact monetary amounts, idempotent interval ingestion, monotonic commitments and transaction recovery. For a shared channel, serialize the **global payer cumulative balance** separately from per-vehicle ledgers.
- **End-only signed meter support:** interim payments may be based on L1 readings; the signed closing result may trigger adjustment/refund/dispute handling. Do not pretend already-signed incremental proof exists.
- **Stop semantics:** a financial refusal does not turn off a charger; proper hardware/service stop requires an independently implemented authorized CSMS command.
- **SDK operations:** `watchChannel`, on-chain checks and callbacks already exist. Differentiation can only be a higher-level, audited, operated implementation including linearizable CAS, recoverable state, incident response, exposure limits and monitoring.
- **Experimental contract:** `one-way-channel` is explicitly unaudited. Testnet only; nontrivial fund safety risk remains despite a watcher.
- **Public network:** evidence off-chain does not conceal amounts, funding, wallets or counterparty patterns of ordinary channel transfers. Confidential settlement is an unresolved separate research path.

## 7. Why Stellar and why not only MPP

Stellar contributes MPP support, off-chain cumulative channel authorization and Soroban/token settlement. We use existing `@stellar/mpp` and an experimental one-way-channel as instructed, not a new on-chain unit-pricing contract.

A direct integration remains a credible competitor. UsagePay deserves existence only if verified evidence provenance, tariff/policy replay, cross-domain adapters and reliable channel operations impose reusable complexity **not economically justified for each operator to rebuild**.

One SDK function, a tariff spreadsheet and an evidence hash are insufficient to establish a durable defensible product. The actual defensible work, if any, lies in trustworthy evidence interchange, integration/reconciliation semantics and possibly managed channel reliability. Prove in code and pilots.

## 8. Competitive map and differentiation constraints

- **Stellar native:** SDK and channel, ROZO (digital variable-cost MPP), StellarPay, Paykit, ApiCharge, SolarGrid/PAYGo experiments.
- **Cross-chain/metrology:** GraphTally's receipt aggregation; IoTeX/peaq device attestation; DeCharge and Share&Charge EV ecosystems; x402 `upto` and metered digital charging.
- **Enterprise incumbents:** CSMS/roaming hubs, payment services, invoicing and charge-data reconciliation.

Publicly funded projects prove ecosystem activity, **not** exclusive market boundaries or production adoption. “We found no public exact equivalent in the surveyed sources” is acceptable; “nobody has ever built this” is not.

## 9. Hackathon scope — product acceptance boundary

The validated product question is whether independently checkable evidence adds value beyond OCPP/CSMS, OCPI and native MPP. **The authoritative P0/P1/P2 feature list, tests, timing, diagrams and demo sequence are in [01.1 §§8–9](../../01.1-usagepay-technical-architecture-and-roadmap.md).** Commercial claims must stay narrower than the demo: simulated metrology is not certified; payment signatures do not enforce measured energy on-chain; provisional readings may not be signed; financial refusal does not stop a charger.

## 10. Open-source versus managed product split (mandatory roadmap decision)

**Product A — Evidence Infrastructure.** Distributable library, adapters, verification schema/test vectors. Potential users: developers and operators integrating meter evidence with settlement. Revenue optional; value may be open-source/public-good adoption.

**Product B — Managed Settlement Operations.** Managed watcher, automatic close and safe recovery, alerting, SLAs, reconciliation, uptime and key/custody boundaries. Potential revenue: recurring platform/service fees. Depends on sufficiently widespread Stellar channel usage and operational willingness to pay. Never imply the SDK lacks watcher support.

**They can complement each other, but they are not the same commercial proposition.** Preserve separate unit economics, growth signals and go/no-go gates. A library can succeed without a SaaS business; managed operations can fail even if the library is excellent.

## 11. Go / narrow / kill criteria and risk register

| Risk | Evidence available | Action / gate |
|---|---|---|
| Reusable bridge already covered in target vendor's CSMS | Not fully mapped | Direct integration spike + operator interview -> A if sufficient |
| No stablecoin appetite from fleets/CPOs | Unknown | Pilot request and total-cost comparison -> C only with interest |
| Signatures do not cover intermediate usage | OCA confirms this can occur | Interval evidence labels and terminal reconciliation |
| Fake physical activity / meter key provenance | Simulated demo not real assurance | Clear trust levels, device key verification in pilot |
| Public counterparty and amounts leak | Standard public chain property | B2B disclosure requirements + VeilPay research gate |
| Channel recipients miss refund window | Experimental contract requirement | Watcher, alerts and security review; testnet only |
| Multi-vehicle sharing races / duplicates | SDK warns on concurrency | CAS and serializable channel totals |
| High ramp/treasury and prefund costs | Not measured | All-in comparison; reject premature fee savings claim |

**Best current classification: Outcome B**, a plausible OSS/reference-integration opportunity. **Outcome C** is contingent; it is not granted by a hackathon or SCF award. **Outcome A** remains true for several commodity payment cases and could become true for the entire scope after operator validation.
